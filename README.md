# 🏦 Vault & Crest Bank — Multi-Portal Banking System

A 5-portal bank management web app: **Manager, Cashier, Customer Service Employee (CSE),
Loan Manager**, and **Customer**. Built with Flask + Supabase (PostgreSQL).

---

## 📁 Project Structure
```
bank_project/
├── app.py                       ← Flask backend & all routes
├── requirements.txt             ← Python dependencies
└── templates/
    ├── portal_select.html       ← Landing page — pick your portal
    ├── staff_login.html         ← Shared access-code login (Manager/Cashier/CSE/Loan Manager)
    ├── customer_login.html      ← Customer login (Email + Bank ID)
    ├── cse_dashboard.html       ← CSE portal — client onboarding & record management
    ├── manager_dashboard.html   ← Manager portal — branch-wide analytics
    ├── cashier_dashboard.html   ← Cashier portal — balance lookup, deposit/withdraw
    ├── loan_dashboard.html      ← Loan Manager portal — grant loans, EMI tracking
    └── customer_dashboard.html  ← Customer portal — balance, statement, EMI payment
```
There is **no `signup.html`** anymore — the CSE portal is the only way new customers get
registered, and staff portals no longer use a username/password signup flow at all.

### Table 4 — `bank_vault` (new — the bank's central cash reserve)

| Column | Type | Notes |
|---|---|---|
| `id` | `int4` (Primary Key) | Always `1` — this is a single-row table |
| `Cash_Balance` | `numeric` | The bank's available cash. Starts at ₹10,00,000 and is auto-created by the app the first time it's read if the row doesn't exist yet (but the **table itself** must exist — see SQL below). |

**How this number moves:**
- **+amount** when a customer deposits (cashier portal, or the initial deposit at CSE onboarding)
- **−loan amount (principal only)** when a loan is granted — the principal physically leaves the
  bank's reserve and moves into the customer's account balance
- **+interest portion only** when a loan EMI is repaid (by the customer or the Loan Manager's
  "Deduct EMI" button). Each EMI is split into its principal and interest portions using the
  loan's fixed principal/interest ratio (`split_emi_payment()` in `app.py`). Only the interest
  portion returns to the reserve — the principal portion doesn't re-enter as "new" cash, since
  it's just the same principal cash leaving the customer's balance that already left the vault
  at disbursement.
- **−amount when a customer withdraws, MINUS a "loan cushion"**: if the customer has an active
  loan, the system checks `Outstanding_Principal` on that loan (the principal still owed) before
  deducting anything from the vault. Only the portion of the withdrawal that EXCEEDS the
  outstanding principal reduces the reserve — the rest is assumed to be loan money that already
  left the vault at disbursement, so it doesn't get deducted twice. A customer with no loan has
  their full withdrawal amount deducted from the reserve as normal.
  ```
  vault_deduction = max(0, withdrawal_amount - outstanding_loan_principal)
  ```
- A loan **cannot be granted for more than the current `Cash_Balance`** — the Loan Manager portal
  checks this and rejects oversized loans with a clear error, since the loan principal is paid
  directly out of the reserve

This is intentionally a **separate figure from "Total Customer Deposits"** (the sum of every `Balance` in `registration`) — the Manager dashboard now shows both side by side, since they answer different questions: "how much cash does the bank physically hold" vs. "how much does the bank owe its depositors."

  "Remaining_Amount" numeric,
  "Outstanding_Principal" numeric,
  "Status" text default 'ACTIVE',
  "Granted_By" text,
  "Granted_At" timestamptz default now()
);

-- If your "loans" table already exists from before, just add the new column:

-- For any EXISTING active loans, backfill it to match Loan_Amount as a starting point:

## 🔐 Security changes made
- **PINs are bcrypt-hashed** (`Pin_Hash`) instead of stored as plaintext.
- **Card numbers are stored as plain text** in `Card_No` — this is intentional, not an
  oversight: your separate ATM project needs to look up accounts by the real card number, so
  hashing it would break that integration. If the ATM project ever needs to verify a PIN against
  this same database, it should call `bcrypt.checkpw()` against `Pin_Hash` the same way this app
  does — never compare PINs in plaintext.
- The CSE success message shows the raw card number and PIN once at creation time so they can be
  handed to the customer — after that, the PIN is unrecoverable (hashed), but the card number can
  always be looked up again from `Card_No` since it's stored as-is.
- The customer's bank-statement PIN check uses `bcrypt.checkpw` against `Pin_Hash`.
- Staff portals authenticate purely by access code (no DB lookup, no stored credentials) —
  exactly as you specified in point 13.
- The `users` table and all signup flows have been removed.

## 🧮 EMI Formula (as specified)
```
Total Interest = (Principal × Rate × Time_in_years) / 100
Total Payable  = Principal + Total Interest
Monthly EMI    = Total Payable / Tenure_in_months
```
Tenure can be entered in years and months in the Loan Manager portal — months are auto-summed
(`years × 12 + months`) before any calculation happens.

## 🤖 Auto EMI deduction
The Loan Manager portal has a **"Deduct EMI"** button per active loan that pulls the EMI
amount out of the customer's `Balance` and logs it to `transactions`. This is wired as a manual
trigger for now — to make it fully automatic on a calendar schedule, point a daily cron job (or
a Supabase Edge Function / scheduled trigger) at the same logic in `loan_deduct_emi()` in
`app.py`. I left it manual rather than wiring a real cron job since this environment can't run
a persistent background scheduler — happy to wire one up if you tell me where you're hosting
(e.g. Hugging Face, Render, a VPS) since the right approach differs by host.
